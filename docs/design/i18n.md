# Internationalisation: Italian first, built for the tenth language

**Status:** specification. Nothing implemented.
**Check:** `grep -rn 'fluent' Cargo.toml` exits 1 — no localisation runtime is a dependency.

The ask is an Italian version of sipnab, as the first step toward many
languages. The trap in that phrasing is that "sipnab" is three products with
three different translation problems, and doing them together is how a
localisation effort stalls halfway. This picks one, in an order where each
phase is useful alone.

## The three surfaces, and why they are not one project

| Surface | Size | Mechanism | Who translates |
|---|---|---|---|
| Website | 26 mirrored pages + templates | Zola native i18n | a translator, prose |
| Docs | 28 pages under `docs/`, each mirrored | Zola native i18n | a translator, technical prose |
| CLI / TUI runtime | every user-facing string in `src/` | `fluent-rs` | a translator, but gated by code changes first |

They differ in the thing that matters: **the website needs no Rust change and
no new dependency**, while the runtime needs a localisation framework wired
through every message site before a translator can begin. Shipping an Italian
website is a week; shipping an Italian CLI is a refactor.

## Phase 1 — the website, in Italian

**Recommended scope, and the only phase this document commits to.**

Zola has first-class multilingual support, so this needs no new tooling:

```toml
# website/config.toml
default_language = "en"

[languages.it]
title = "sipnab"
description = "…"
generate_feeds = true
```

Content gets sibling files: `content/docs/install.md` and
`content/docs/install.it.md`. Zola serves the second at `/it/docs/install/`,
generates a per-language sitemap, and `{{ trans(key="…", lang=lang) }}` pulls
UI strings from `[translations]` tables in `config.toml`.

**What must change beyond adding files** — this is the part a naive plan
misses, because this repository polices its documentation with ratchets:

1. **`docs_drift_test` counts TRACKED markdown.** Every `.it.md` moves that
   number. The count is fine to raise; it must be raised *deliberately*, from
   a failing run.
2. **`no_documentation_table_repeats_a_row` walks every table.** A translated
   page duplicates every table it contains, so this ratchet moves by the
   number of tables translated.
3. **Both site generators have `PAGES` maps with no language dimension.**
   `build-site-pages.py` and `build-site-internals.py` map one source to one
   output. They need a language axis, or Italian pages must be authored
   directly under [`website/content/`](https://github.com/NormB/sipnab/tree/main/website/content) and excluded from the generated set —
   and `docs_to_site_map_is_complete` must agree with whichever is chosen.
4. **`build-wiki.py` likewise.** The wiki is generated from `docs/`; either it
   grows a language dimension or Italian is scoped out of the wiki and the
   test that asserts every internals page publishes somewhere must say so.
5. **Vale has no Italian dictionary.** It runs over `docs/` and
   [`website/content/`](https://github.com/NormB/sipnab/tree/main/website/content), and every Italian word will read as a spelling error.
   Either scope Vale to English paths (`--glob`), or add an Italian
   `Vocab`/style. Scoping is honest and cheap; adding a real Italian style is
   the better long-term answer and can come later.
6. **`link_integrity_test` pins page counts and walks internal links.**
   Translated pages must link to translated siblings, or every Italian page
   quietly bounces the reader back into English.
7. **Version markers and download lines are pinned per page.** A translated
   `install.it.md` carries the same `SIPNAB_VERSION=` markers, and
   `docs_current_version_markers_match_cargo` will check them. That is
   correct — a stale version in the Italian install page is exactly as
   dangerous — but it doubles what the post-release move has to touch, and
   that move has already been missed once.

**Order of work.** One page end to end before any bulk translation:

1. `[languages.it]` in `config.toml`, plus a language switcher in `base.html`.
2. Translate **one** page — [`docs/install.md`](https://github.com/NormB/sipnab/blob/main/docs/install.md) is the right choice, because it
   is the page a new user actually needs and it exercises the version-marker
   gates immediately.
3. Fix whatever ratchets and generator maps that one page breaks. **That is
   the real deliverable of phase 1** — after it, every further page is
   mechanical.
4. Only then translate the rest, in reader-value order: install →
   troubleshooting → the TUI walkthrough → the SIP reference pages.

## Phase 2 — the CLI, with Fluent

**Not committed to here.** Scope it separately once phase 1 is done.

The industry-standard choice for Rust is [Project
Fluent](https://projectfluent.org) via `fluent-rs`. It is what Firefox uses,
and it is chosen over gettext for asymmetric translation: Italian gender
agreement and plural rules do not map onto `.po` files without contortion,
where an FTL file expresses them natively.

```ftl
# it/cli.ftl
dialogs-found = { $count ->
    [one] Trovato { $count } dialogo
   *[other] Trovati { $count } dialoghi
}
```

Locale negotiation via `unic-langid` + `fluent-langneg`, honoring `LANG` /
`LC_ALL` with an explicit `--lang` override.

The reason this is a separate project: **every user-facing string in `src/`
must first become a keyed lookup**, and this crate has ~4,700 tests, many of
which assert on exact English output. Those assertions must move to keys or
run under a forced `en` locale, or the suite becomes locale-dependent and
fails wherever a developer's `LANG` differs. That is the real cost, and it is
paid before a single Italian string exists.

**Do not translate log or trace output.** Operators grep it, and search
results, runbooks and Stack Overflow answers are all in English. Fluent covers
what a *user* reads; `tracing` output stays English.

## Phase 3 — translation workflow

Once more than one language exists, hand-maintained files stop scaling.
[Weblate](https://weblate.org) self-hosts, speaks Fluent and Markdown natively,
and opens pull requests — which keeps every gate in this repository in the
path. Crowdin is the hosted alternative and is free for open source.

Not needed for phase 1: one language by one translator is a pull request, not
a platform.

## What is deliberately excluded

- **Machine translation without review.** A confidently wrong Italian
  description of a security tool is worse than an English one the reader knows
  they are reading.
- **Translating [`CHANGELOG.md`](https://github.com/NormB/sipnab/blob/main/CHANGELOG.md).** It is a historical record; entries are dated
  and immutable, and a partially translated history is worse than an English
  one.
- **Translating error strings that name RFC terms.** `Call-ID`, `INVITE`,
  `SIP/2.0` are protocol tokens, not prose. They stay.

## The measure of success for phase 1

A reader arriving at `sipnab.com/it/` can install sipnab and read the
troubleshooting page in Italian, every existing gate still passes, and adding
the eleventh page requires no new decisions — only translation.
